# 문제 정의와 설계 변경 배경

## 문제 정의

언어모델에 대한 요청은 "이거 정리해 줘", "아까 그거 좀 더 공식적으로", "보고서 반으로 줄여 줘"와 같이 짧은 경우가 많습니다. 이러한 요청에는 다음 두 가지 정보가 생략되어 있습니다.

- **작업 대상**: '이거', '아까 그거'가 대화 중 어떤 결과물을 가리키는지
- **작업 방법**: 어느 정도로, 어떤 기준으로, 어디까지 작업할지

언어모델은 생략된 정보를 스스로 추론합니다. 추론이 맞으면 편리하지만, 틀리면 사용자가 원하지 않은 결과물이 만들어지거나 삭제해서는 안 되는 파일이 삭제될 수 있습니다. 반대로 모든 생략 정보를 질문하면 사용자의 부담이 커집니다.

이에 본 프로젝트는 문제를 다음과 같이 정의하였습니다.

> **작업을 시작하기 전에, 요청을 그대로 진행해도 되는지 사용자에게 확인해야 하는지를 판단한다.**

계획 수립과 문서 작성 작업을 대상으로, 모호성을 다섯 가지 유형(지시 대상 · 생략 · 정도 · 비교 · 범위)으로 나누어 분석하는 것에서 출발하였습니다.

---

## 설계 변경 배경

### 1. 모호성 탐지에서 질문 필요성 판단으로

초기에는 모호한 표현을 빠짐없이 찾는 데 집중하였습니다. 그러나 실제 언어모델과 연동한 평가에서는 자동 테스트를 모두 통과했음에도 **문맥으로 해소할 수 있는 요청에 대해 15건의 불필요한 질문**이 발생하였습니다.

모호한 표현이 존재하는 것과 사용자에게 질문해야 하는 것은 별개의 문제였습니다. 이에 언어모델은 해석 후보, 문맥 근거, 작업 영향만 분석하고, 질문 여부는 **작업 영향 × 후보 수 × 근거 강도**를 기준으로 결정 규칙이 판단하도록 역할을 분리하였습니다.

### 2. 최근 문맥 우선

대화가 길어지면 언어모델은 오래된 대상과 최근 결과물을 같은 비중으로 판단하였습니다. 일반적으로 '이거'는 가장 최근에 언급된 대상을 가리킵니다. 이에 **최근 대상을 우선하고, 화제가 바뀌면 이전 대상을 후보에서 제외하며, 사용자가 과거 대상을 명시한 경우에는 해당 대상을 따르는** 규칙을 추가하였습니다.

같은 시기에 긴 첨부 문서의 뒷부분을 분석하지 못하는 문제를 확인하여, 입력 한도를 4,000자에서 12,000자로 확대하고 생략된 부분을 추론하지 않도록 안내를 추가하였습니다.

### 3. 해석이 여러 개 가능한 경우와 질문이 필요한 경우의 구분

"정기 모임 안내 메일 써 줘"라는 요청에는 날짜, 장소, 참가비가 지정되어 있지 않지만, 이를 모두 질문하는 것은 적절하지 않습니다. 이에 **결과물의 핵심이 되는 정보**(자기소개서의 실제 경험처럼 임의로 작성하면 안 되는 정보)만 질문하고, **주변 정보**(안내문의 날짜·장소)는 빈칸으로 남기도록 기준을 수정하였습니다. "조금 더 간결하게"와 같은 정도 표현도 질문하지 않고 처리하도록 하였습니다.

### 4. 규칙 수정으로 인한 새로운 실패

불필요한 질문을 줄이는 과정에서 새로운 문제가 발생하였습니다. 발표 대본, 예상 질문, 제목 후보를 차례로 작성한 뒤 "아까 그거 좀 더 공식적인 말투로"라고 요청하면, '아까'가 가리킬 수 있는 결과물이 여럿인데도 언어모델이 **가장 최근 결과물 하나로 확정**하였습니다. 이전에는 다른 질문이 보조적인 안전장치 역할을 하고 있었으나, 질문 기준을 조정하면서 그 역할이 사라진 것입니다.

언어모델의 판단에만 의존하면 같은 유형의 실패가 반복될 수 있습니다. 이에 **언어모델을 사용하지 않는 규칙**이 대화 구조(결과물의 수, '아까'와 같은 과거 지시 표현, 되돌리기 어려운 외부 작업 여부)를 별도로 확인하고, 언어모델의 판단과 충돌하면 질문으로 전환하는 안전 검사를 도입하였습니다.

### 5. 선택적 분석 도입

판단 기준이 정교해질수록 분석 지침이 길어졌고, 모든 요청에 정밀 분석을 수행하는 비용도 증가하였습니다. 그러나 대부분의 요청은 명확한 요청이었습니다.

이에 **위험도가 높은 요청만 정밀 분석**하는 구조로 변경하였습니다. 초기에는 규칙만으로 위험 요청을 선별하였으나, 개인적인 사정이나 표현 변형처럼 규칙으로 포착하기 어려운 유형이 계속 확인되었습니다. 최종적으로 확실한 위험은 규칙이 판단하고, 나머지는 경량 모델의 위험 점수로 판단하는 **하이브리드 방식**을 적용하였습니다.

### 6. 질문 전달 방식 개선

MCP가 생성한 질문을 클라이언트 언어모델이 다시 작성하면서 질문이 길어지고, 후보가 질문 본문과 선택지에 중복으로 표시되는 문제가 있었습니다. 이에 사용자에게 보여 줄 문구를 별도로 생성하고, 도구 설명에 "질문을 수정하지 않고 그대로 전달할 것"을 명시하여 질문 길이 중앙값을 103자에서 59자로 줄였습니다.

## 평가 방식 변경 배경

시스템 설계와 함께 평가 방식도 여러 차례 보완하였습니다.

- **유형 일치 기준에서 행동 중심 기준으로**: 초기 평가는 모호성 유형까지 정답과 일치해야 통과로 판정하였습니다. 그러나 유형을 다르게 분류하더라도 필요한 질문을 했다면 모호성은 해소된 것입니다. 이에 "질문이 필요할 때 핵심을 질문했는가, 질문이 필요하지 않을 때 진행했는가"를 기준으로 평가 방식을 변경하였습니다.
- **후보를 모두 처리한 응답의 재평가**: 한때 평가 기준은 후보를 모두 처리한 응답을 안전한 처리로 판정하였습니다. 그 결과 사용자가 원하지 않은 범위까지 작업한 응답이 문제없는 것으로 집계되었습니다. 이를 실패로 판정하도록 기준을 수정하자 조건 간 차이가 드러났습니다.
- **개발 데이터와 평가 데이터의 분리**: 규칙 개선에 사용한 사례로 성능을 측정하면 실제보다 높게 나타납니다. 이에 평가마다 평가셋을 새로 구성하였습니다(Final-100 → Final-120 → Decision-150).
- **MCP 형태의 필요성 검증**: 개발 과정에서 정리한 판단 기준을 프롬프트 지침 4줄로만 제공한 조건을 비교 대상으로 포함하여, MCP 구조가 필요한지를 직접 확인하였습니다.
- **판단 평가와 응답 평가의 분리**: 최종 응답 점수에는 문장 생성 능력, 도구 호출 여부 등 판단 이외의 요인이 함께 반영되었습니다. 이에 판단 결과만 별도로 제출받아 채점하는 Decision-150을 추가로 설계하였습니다.
